# 04 — Running FitAdapt on Meridian

> Status: **draft**, owned by the delivery lead (PE-14). Meridian document DOC-04 (PRJ-206, Gate 1).
> Meridian: <https://github.com/mliad313sn/Meridian> — self-hosted, Apache-2.0. Requires **5.9.1 or later** (earlier versions cannot import a book: [PR #14](https://github.com/mliad313sn/Meridian/pull/14)).

## 1. What lives where

Meridian describes itself as a portfolio and governance record, *not* a task manager or agile board. We use it that way:

| Concern | System of record |
|---|---|
| Phases, module schedule, dependencies, gate dates | **Meridian** (projects, activities, gate milestones) |
| Gate evidence and who approved it | **Meridian** documents, each pointing (`uri`) at a file in this repo at a pinned commit |
| Risks, issues, assumptions, dependencies | **Meridian** RAID (seeded from the legal risk register) |
| Decisions and actions from meetings | **Meridian** meetings (agendas generated from the book) |
| Scope/date/budget changes | **Meridian** change requests |
| Code, specs, ADRs, module status, sign-off records | **Git** (this repository) |
| Day-to-day work of a `/goal` run | The branch and its PR |
| Friction with Meridian itself | Meridian work items (PRJ-207) mirrored as issues on the Meridian repo (`05`) |

## 2. How the plan maps onto Meridian

| FitAdapt | Meridian |
|---|---|
| The product, to market readiness | Programme **FAD** |
| Phase 0 … Phase 4 (`GOALS.md`) | Projects **PRJ-201 … PRJ-205**, site-governed |
| Gate 0, counsel, Expert Advisory Council | Project **PRJ-206**, group-governed |
| Running Meridian and contributing back | Project **PRJ-207**, site-governed, with a board |
| Module M00 … M20 | One activity per module, with its dependencies; the cross-phase ones as cross-project dependencies |
| FitAdapt Gate *N* (exit of a phase) | That phase project's Meridian **Gate 3 — Readiness**; evidence document "Gate *N*: exit evidence and sign-off records" |
| Council reviews | PRJ-206 activities G11–G14 |
| Legal risk register + committee risks §11 | RAID `RSK-01…20`; open questions as `ISS`, `ASM`, `DEP` |
| Team roles and council seats | People `PE-01…14` and `PE-21…31`, one site `HQ` |

Meridian 5.9 has four fixed gates per project (Mandate, Design authority, Readiness, Benefits). FitAdapt's gates are programme-level, so each phase's exit gate sits on Meridian's Gate 3. A configurable gate ladder already exists on an unmerged Meridian branch ([#3](https://github.com/mliad313sn/Meridian/issues/3), [#15](https://github.com/mliad313sn/Meridian/issues/15)). When it reaches `main`, declare FitAdapt's own ladder on programme FAD before creating any further project.

Budgets are **zero on purpose** until the sponsor baselines them at Gate 0 (RAID ASM-03). Meridian then reports "no cost baseline" rather than inventing an index (MER-04, fixed in 5.9.1).

The whole book is generated by `pmo/meridian/build-book.mjs`, so changing the plan starts in the repo: edit, regenerate, review. After go-live, the team edits **in Meridian**, and the generator is only used to rebuild a training instance.

## 3. Accounts and authority

Create these accounts in Meridian's Administration and link each to its person row. Change every seeded demo password first (Meridian `docs/06`, C-04).

| Who | Meridian role | Grant | Can | Cannot |
|---|---|---|---|---|
| Delivery lead (PE-14) | admin | — | Instance, accounts, settings, backup | Should not approve gate evidence (use a second, group account for that if ever needed) |
| Sponsor (PE-01) | group | programme FAD | Approve gate evidence, change requests, re-baseline | — |
| Product Owner (PE-02) | group | programme FAD | Run the programme, re-baseline, raise and decide changes within threshold | Approve evidence they own (Meridian enforces it) |
| Engineers, designer, content, QA, compliance (PE-03…13) | site | site HQ | Update activities, RAID and work items on phase projects, raise changes | Re-baseline, approve gate evidence on their own projects, edit governance (PRJ-206) |
| Council members (A1…B4, C1) | viewer | programme FAD | Read everything in the programme, including gates and minutes | Approve evidence directly — see `03` §5 and Meridian [#16](https://github.com/mliad313sn/Meridian/issues/16) |

We checked this against Meridian's `shared/rbac.js`. A site account on HQ can write schedule and RAID on PRJ-202 but not on PRJ-206. The PO can re-baseline but cannot approve a gate document they own.

|---|---|---|---|
| **Weekly delivery review** | Monday 09:30 UTC, 30 min | PO | Actions, escalated RAID, gates in the next 45 days, then the **dogfooding triage** (5 min: new friction, PRs in flight) |

In the first generated agenda (28 Sep 2026) the top decisions were already the right ones: *PO not yet named*, *all council seats open*, *the committee was simulated*, *budget not baselined*.

## 5. Gate evidence, step by step

1. The module PR merges, and the status file lists what was built and what is still `validated:false`.
2. The PO updates the gate's evidence document in Meridian: status *In review*, and `uri` = the GitHub URL of the evidence file **at a commit SHA** (a branch URL can change under the reviewer). `documentHosts` is set to `github.com` by `bootstrap.mjs`.
3. Council positions come back as sign-off records (`03` §5).
4. The sponsor approves the document in Meridian. The PO can't approve documents they own, and Meridian enforces that.
5. Meridian's gate lock (`gateLock: true`) keeps the phase from advancing until every evidence document for that gate is approved and has a `uri`.

## 6. Standing it up

```bash
git clone https://github.com/mliad313sn/Meridian && cd Meridian
npm ci && npm run seed && npm run dev          # 5.9.1+: the book persists in server/.data/pgdata
# in this repo:
MERIDIAN_EMAIL=admin@meridian.example MERIDIAN_PASSWORD=meridian-admin-2026 \
  node pmo/meridian/bootstrap.mjs               # refuses to overwrite a non-empty book without --yes
```

Then create the accounts (§3) and change the demo passwords. Before anything real is recorded, close Meridian's three operational blockers: a **tested backup**, a **second instance**, and a written **security policy** (Meridian `SECURITY.md`; our activity D02, RAID DEP-03). For a lasting instance, use PostgreSQL (`DATABASE_URL`), not PGlite. Meridian itself calls PGlite a trial engine.
