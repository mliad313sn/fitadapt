## Deviations, with reasons

1. **The config lives in `packages/engine/src/config/`**, not in a top-level `packages/engine/config`. `rootDir` is `src` and every earlier module keeps its config there. `ENGINE_CONFIGS` lists them all.
2. **`ENGINE_VERSION` bumped from 0.1.0 to 0.2.0.** The M07 first-session prescriptions change: loads are rounded to the equipment when loads are known, and S5 now counts future-dated references. The server refuses 0.1.0 sessions. The literal `'0.1.0'` in three places of `apps/api/test/integration/profile.test.ts` became `ENGINE_VERSION`; the assertion is unchanged.
3. **S5 counts references dated in the future.** The existing M07 test `first-session.test.ts` expected 115 kg for a load "dated after the clock". It now expects the S5-capped 110 kg. The assertion is still there and stricter, and a comment explains why: otherwise a clock moved backwards loosens the cap.
4. **The "weekly e1RM-based load increase ≤ 10 %" is enforced on the prescribed load** for each exercise. The ceiling is 1.1 × the lowest prescribed or performed load of that exercise in the last 7 days. When a new e1RM comes from an assessment, the load derived from it also passes through this cap.
5. **The S3 red-flag flow is a hook, not the full flow.** The symptoms list, the seek-care notice, the lock and a self-attestation button are in place. M05 builds the full review flow and who may attest.
6. **The rest-timer lock-screen notification is a port** (`RestNotifier`). It does nothing until M13 wires expo-notifications. The timer itself stays correct, because it is an end time.
7. **`set_logs` are not validated on the server** beyond the existing legacy policy (append-only). Sessions and execution logs are validated. A set log has no prescription of its own.
8. **The server re-runs S5 over its own stored history.** A device that trained offline on another device the same week can have a session refused (`safety.s5.load_above_ceiling`). See open question 2.
9. **Loads per place (`EquipmentLoads`) have no entry screen yet.** When a place has none, gym places use the `INCREMENT_CONFIG` defaults and other places use none: an unknown load is never invented, and the user chooses it (`session.load.self_select_light`).
10. **On a program rest day no session is offered** ("rest day", no session invented). Training on a rest day would need a reflow (M08) first.
11. **Resuming a started session after the app is killed is not supported yet.** Every set already logged is stored, and a new session can start.
12. **No device, no Docker, CI not run on GitHub.** Journeys are proven with jest-expo over sql.js. Integration tests run on local PostgreSQL 16 and Redis. The Maestro flow is not executed.
13. **Existing tests and config changed; no assertion removed or loosened:**
    - `packages/engine/src/session/first-session.test.ts` (M07): the S5 expectation 115 → 110 (deviation 3).
    - `apps/api/test/integration/profile.test.ts`: `'0.1.0'` → `ENGINE_VERSION` (deviation 2).
    - `packages/sync/src/test/sync.test.ts`: new assertions that `workout_sessions` and `execution_logs` are append-only.
    - `packages/legal/src/release-defensibility-claims.test.ts`: a new M02 test (`rulesVersion`, `safety.attested`).
    - `packages/i18n/src/guilt.test.ts`: a new test over the workout copy.
    - `apps/mobile/__tests__/routes.tsx` (the route map, which has no assertions): the `workout` route was added.
    - `apps/mobile/jest.config.js`: `testTimeout: 30_000`. This is the same budget that engine, exercise-library and legal already use. The existing onboarding and assessment journeys take 3–4 s alone and hit the 5 s default under turbo's parallel workspace run once the M02 suites were added. Root cause: CPU contention between 24 parallel tasks, not a hang. No assertion or run count changed.
    - The session assessment schemas moved from `packages/shared/src/assessment.ts` to `session.ts` and are re-exported with the same names.

## Open questions

1. **S5 granularity.** With an inclusive 7-day window, a user who trains an exercise exactly every 7 days on equipment whose next step is more than 10 % (for example 2 kg dumbbells at 10 kg) can stay capped forever, and the engine moves them up the ladder instead. Is that the intended reading of S5, or should the window be exclusive? (A3, PO)
2. **Several devices offline in the same week.** The server's S5 check can refuse a session one device made without the other's history. The record stays rejected in the outbox. How should the app show this? (M19, PO)
3. **Are `set_logs` health data** under the records of processing (B1)? They are append-only and consent-gated in the history selector, but not a health collection on the server (the legacy M00 policy).
4. **Who may attest the S3 medical review**: self-attestation (current hook), or a clinician? (A1, M05, counsel)
5. Should **rest-day training** be offered by building a reflow first (M08)? (PO)
6. Should a changed engine version also re-derive the golden files for **every earlier module's** events, or only for M02 sessions (M07 open question 6)? (M19)
