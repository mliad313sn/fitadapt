## M02 open questions answered

- **"Who may attest the S3 medical review" (M02 open question 4).** The spec takes S3 from the vision: "locks intensity until the user attests medical review". So **the user self-attests**, and M05 makes that deliberate:
  - two steps (statement, then "I confirm"; "Not yet" keeps the lock);
  - a versioned statement that a doctor or another qualified health professional has checked them since the warning signs and agrees they can exercise again;
  - `statementVersion` in the log and `safety.attested` in the defensibility log;
  - a triggered deload for 7 days after it.
  - Still open for **A1** and counsel: whether a clinician must confirm instead, a minimum wait, and the wording.
- **M02 deferred "full red-flag and medical-review flow; triggered deloads; next-morning pain check"**, and **"Readiness input"**: built (above).

## Deviations, with reasons

1. **The Maestro flow is not executed** (no device or emulator). The journey is proven in jest-expo through the real router and on-device SQLite with the network failing, for three jurisdictions. A test checks the flow's testIDs against the app.
2. **`ENGINE_VERSION` 0.2.0 → 0.3.0; `SESSION_RULES_VERSION` 0.1.0 → 0.2.0; `PROGRAM_RULES_VERSION` 0.1.0 → 0.2.0.** Every plan now carries its warm-up and a possible cool-down, triggered deloads change sets, and scheduled deload weeks change. The server refuses 0.2.0 sessions and 0.1.0-rules programs. The goldens changed deliberately:
   - `P{1..6}.sessions.json`:
     - the cool-down is added when time is left: `cooldown.after_session` in the plan codes, and `estimatedMinutes` up by 2–5 min (e.g. P1 34.4 → 39.4 of 40 min);
     - safety events carry engine version 0.3.0;
     - a new `warmUp` projection line lists the general block, ramp-up sets and drills for review;
     - no set, load, reserve or exercise changed.
   - `P{1..6}.program.json`: only deload weeks changed. Their sets are now 50 % of the accumulation week before (for example P1 week 6 went from 8 + 8 + 5 to 5 + 4 + 3), and three deload weeks lost a misleading `program.volume.time_limited` code.
3. **`PAIN_CONFIG.amberPainScore` 3 → 4.** The spec says "green ≤ 3, amber 4–5". M02's 3 was an engineering placeholder that pointed to M05. S2 (red ≥ 6) is untouched. The M02 test for this (`session-safety.test.ts`) is unchanged and passes.
4. **Red now persists until a later session reports below 6.** M02 cleared it on any later report below 6. This is stricter (S2 "in the next session"). The M02 tests are unchanged and pass: reports without a session keep the old behaviour between themselves.
5. **Readiness "trims volume by one set per exercise"**: this is the existing M02 'reduced' rule. It also leaves out the accessory exercises and adds a rep in reserve, as M02 decided. The goal's "one set per exercise" holds for every exercise that stays. Swaps suggested by readiness (spec "or suggests swaps") are not built.
6. **Triggered deloads cannot be declined** in v1: the pain and red-flag triggers are safety-adjacent. Every set can still be skipped (L4). The KPI "deload acceptance rate" needs M18 and can be measured as completion. Rounding: at least half the sets stay, so a session with 3 sets loses 1 (33 %); from 5 sets up, a deload removes 40–50 %.
7. **"Alternative grips and variants"** are guidance on the exercise (`session.amber.<joint>`: a neutral grip or a comfortable range of motion) plus the seed's existing substitutes, such as ring rows. No new seed exercises were added: M06 owns the seed, and new entries need A2/A3 review and licensed media.
8. **The spec's rehabilitation programs are out of scope**, and so are programs for diagnosed conditions. The mobility and balance session is a general wellness session.
9. **Server "that day" for readiness**: for program sessions it is the program date. For a first session without a program it is the plan's UTC date, which can differ from the device's local date near midnight (open question 3).
10. **The server's S2 check is "at least as strict"**, not "equal": a device may be stricter, never looser.
11. **The M02 S2 attribution was fixed.** It named S2 only when the first default candidate loaded a red joint, and missed choices made for another reason (another role this week). The mobile test found this on the seed. Safety was never broken; only the reason code and the L11 event were missing.
12. **Existing tests changed; no assertion removed or loosened:**
    - `packages/engine/src/config/config.test.ts`: the list of engine configs gains `recovery`, whose values are all checked by the same assertions.
    - `apps/api/test/integration/session.test.ts` (M02 S3 test): after the attestation, a session now needs the triggered deload. The test asserts that the session **without** it is refused (`session.deload_mismatch`), then sends it **with** it and keeps the original `['applied']` assertion.
    - `apps/mobile/__tests__/workout.test.tsx` (M02 S3 test): the attestation is two taps now (`workout-attest`, then `workout-attest-confirm`), with a new assertion that the statement is shown. Every original assertion is kept.
    - `packages/exercise-library/src/session.test.ts`: the golden projection gains the `warmUp` lines; goldens regenerated as in deviation 2.
    - `packages/sync/src/test/sync.test.ts`: a new assertion that `readiness_checks` is append-only.
    - `packages/safety/vitest.config.ts`: `testTimeout: 30_000`, the budget engine, legal and exercise-library already use. The 20,000-run adversarial property takes about 1 s alone and 10.4 s under turbo's parallel run, which hit the 5 s default. Root cause: CPU contention, not a hang. No run count changed.
13. **No device, no Docker, CI not run on GitHub.** Integration tests run on local PostgreSQL 16 and Redis.

## Open questions

1. **Attestation:** is self-attestation enough (current, S3 wording), or must a clinician confirm? Should there be a minimum wait after a red flag before an attestation counts? (A1, counsel)

6. Should red flags at the check-in also be offered outside the readiness card (for example on Home)? (A1, PO)
