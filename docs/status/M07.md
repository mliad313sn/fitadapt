## Step 0 — M01 defect fixed first (PO review)

M01 deviation 14 / ADR-013: the safety events of a stored screening were appended to the defensibility log **after** the sync transaction, so a failed log write lost them silently (and a retry answered `duplicate`). That broke L11.

- **Fix (`3bff4b8`, `fix(m01): …`)**: `SyncServer` now calls its `onApplied` listener **inside** the store transaction and hands it the store's transaction handle (`ServerStore<TTx>`, `MutationListener<TTx>`; `PgServerStore` exposes `PgServerTx.db`, the PostgreSQL transaction). `profileSyncListener` appends the `safety.event`s with that transaction (`LegalService.recordSafetyEvent(userId, payload, tx)`), which is the ADR-009 "same transaction" rule. A failed log write rolls back the change **and** its idempotency record and fails the push (HTTP 500); the device keeps the mutation in its outbox and retries, and the retry is applied (not answered `duplicate`).
- **Tests**: `apps/api/test/integration/profile.test.ts` › `stores a screening and its safety events atomically: a failed log write persists neither, the client retries and then both exist (L11, M01 deviation 14 fixed)` — a real `SyncClient` over HTTP (fetch routed into the app); a `BEFORE INSERT` trigger on `defensibility_events` raises for `safety.event`; asserts: push fails with `HttpError 500`, no `sync_changes` row, no safety event, no `sync_mutations` row, the mutation still pending; trigger dropped; the client's retry → `acked: 1`, one screening, one S1 event, chain verifies. `packages/sync/src/test/sync.test.ts` › `runs the listener inside the sync transaction: if it fails, the change is not stored and a retry applies it (L11)` (memory store).
- Docs: `docs/status/M01.md` deviation 14 and `docs/adr/ADR-013` consequences are struck through and marked **"fixed in `3bff4b8`"** (history kept); ADR-009's "same transaction" bullet records the extension (`0b85d8f`).

## Deviations from the spec, with reasons

1. **"Tests stop at RIR 2" is a minimum, not a fixed value.** RIR 2 is RPE 8 on the RIR-based RPE scale; S1 forbids anything above RPE 7 while a screening flag is unresolved. The plan builder asks the M01 `screeningGateCheck` and raises the reserve to RIR 3 (RPE 7) for those users, and shows why. Every instruction for a user without `allowMaxTests` stops at RIR ≥ 2 and never at failure; for users S1 does not cap it is exactly RIR 2. The gating test states both.
2. **Hold tests use an effort reserve**, not reps: "stop while you could still hold on a little longer (effort about 8/10)" (7/10 under S1), plus a time cap.
3. **The 30-second chair stand stops at a reserve.** Jones et al. (1999) count as many stands as possible in 30 s; here the count is paced and stopped at the reserve (C7, S1). Its thresholds are engineering values, not published norms. A1/A3/A5 decide.
4. **Rows share the pull slot with the dead hang.** The M02 pull ladder runs dead hang → scapular pulls → inverted rows → … → pull-ups, so the home "inverted-row reps" test maps onto it (options: incline row, row, strict pull-ups), and counts only after a dead hang of at least 10 s (gate). A home without a low bar or rings offers only the pull-up option (P1: "0 pull-ups" → dead hang, the lowest rung).
5. **`generateSession()` did not exist (M02 is not built).** The goal requires the first session to use the CapacityModel, so the engine now has a minimal, zod-typed, deterministic first-session generator (ADR-014). It covers S1, S2 (via the M06 substitution), S5 (constants) and the time budget; progression, the full slot model, readiness, pain model and supersets are M02/M05/M08.
6. **The CapacityModel is stored as append-only `assessments` records, not as a field of the Profile document** (keeps history for re-assessments, no change to the M01 Profile schema); `useCapacity()` is the profile's capacity. Assessment results are treated as health data (consent required, erased on withdrawal).
7. **Mesocycle end**: M08 is not built, so the re-assessment falls due 4 weeks after the assessment (`defaultMesocycleWeeks`, lower bound of the spec's 4–6 weeks). `reassessmentStatus` already accepts the real end from M08. **Wired by M08** (see docs/status/M08.md): once a program exists, the prompt falls due at the end of the mesocycle containing the assessment (`reassessmentDateFor`, local midnight); the 4-week default still applies without a program.
8. **No timers in the guided screen**: the user times holds and the 30-second window with the stop rule shown, then enters the result. A countdown needs the M02 rest-timer work (background-safe timers).
9. **HR-based estimates**: none. The M07 spec has no heart-rate test (VO2max is out of scope); HR zones are M03.
10. **Engine now depends on `packages/safety`** (to call `screeningGateCheck`); safety depends only on shared, so there is no cycle.
11. **The first session is not logged as a `prescription.issued` event** when it is shown: executed prescriptions and their log entries are M02 (`recordPrescription` now takes the caller's transaction for that).
12. **No device / no Docker / CI not run on GitHub** (as before): journeys proven with jest-expo over sql.js; integration tests on local PostgreSQL 16 and Redis. No Maestro flow for M07.
13. **Existing tests changed, no assertion removed or loosened:**
    - `packages/sync/src/test/sync.test.ts`: one new assertion (`SYNC_COLLECTIONS.assessments` append-only) and one new test for the in-transaction listener; the M01 listener test is unchanged (its listener ignores the new third argument).
    - `apps/api/test/integration/profile.test.ts`: one new test (atomic screening + safety events); two imports added.
    - `apps/mobile/__tests__/routes.tsx` (route map helper, no assertions): the `assessment` route added to `m01Routes`, as M06 did for `library`, because the root layout declares it.
